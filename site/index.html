MapReduce, Measured

A coordinator/worker MapReduce in Go, instrumented until every claim about it is a number with a stated configuration — including the ones that turned out unimpressive.

github.com/aayushhks/map-reduce

How a task actually completes

The interesting part of this system is not that the coordinator hands out tasks. It is what happens when two workers are running the same task at once, or when one dies holding it. Both cases end at the same place: a single arbitration point that decides which attempt is allowed to publish its output.

Task attempt lifecycle
Every attempt writes to a temp file and asks permission before publishing. Exactly one attempt per task is cleared, so a losing backup or a late straggler never overwrites a good result.

Where scaling breaks down

Speedup diverges from the ideal line at the very first added worker and flattens after four, which is the core count of the machine. The interesting engineering is not the speedup number — it is being able to say which of three plausible causes is responsible, with a measurement for each.

Cause 1 — the map phase is bound by cores

Per-task work is identical at every worker count, so growth in task duration is contention. Map task p50 rises from 31.0 ms to 104.3 ms between 1 and 16 workers. Dividing worker count by that inflation predicts the observed speedup closely at low counts: 1.59 predicted against 1.59 measured at two workers, 2.66 against 2.56 at four.

The direct test is restricting the core budget. If the map phase is CPU-bound, the knee must follow GOMAXPROCS — and it does. On one core, adding workers buys nothing at all.

The knee follows the core budget

Cause 2 — the reduce phase is bound by shuffle reads

Reduce tasks spend 88 to 94 percent of their time in I/O, because each of the 16 reduce tasks reads all 160 intermediate partitions: 2,560 file opens per job. The phase floors near 465 ms however many workers are added, and reduce task p50 inflates from 87.7 ms to 328.6 ms as concurrent readers contend. That residual is exactly what the CPU model fails to explain at 8 and 16 workers, where it over-predicts 3.62 against 2.84 and 4.75 against 3.08.

Not the cause — coordinator contention

Coordinator RPC handler time never exceeds 0.2% of job wall clock at any worker count. Handler time is measured from handler entry, so it includes waiting for the global coordinator lock. The single mutex and the linear scan for an idle task are the intuitive culprits, and the measurement says they cost nothing at this scale.

The one optimization, A/B'd

Workers that found no work slept one second before asking again, and were still asleep when the reduce phase began. Lowering that to 10 ms is a single-variable change on the same binary, same input, same seed. The one-worker row is the control: a lone worker never waits, so the setting cannot help it — and it doesn't.

Idle backoff, 1 s against 10 ms

Speculative execution

One worker is made five times slower than the others, stretching every task it runs. With speculation on, a task running past twice its phase median gets a backup attempt on an idle worker, and the first to finish wins the commit.

The headline is a 1.93× improvement. The number that matters more is what happens to it as tasks get smaller.

At 130 tasks the trial ranges overlap completely and 1.03× is noise. Fine-grained tasks with dynamic assignment already absorb a slow worker — it simply claims fewer tasks. Speculation only pays when a single task is large enough that losing it to a slow worker holds up the whole phase. Reported without the granularity sweep, the 1.93× would suggest a general result the measurements do not support.

Fault injection

Workers are real OS processes and kills are real SIGKILL, so a worker dies wherever it happens to be, including part way through writing its output. A scenario counts as correct only if every trial finished with output byte-identical to a clean run.

Recovery is a policy choice, not a property

Recovery is dominated by detection, and detection is a timeout. Sweeping the task timeout on the same scenario moves recovery almost exactly with it, the reap interval adding the small remainder.

Methodology

Every number on this page is rendered from JSON committed in the repository under bench/results/. Nothing here is typed by hand, and nothing is projected or extrapolated.

Hardware and placement

Dataset

Eight public-domain Project Gutenberg books, 3.2 MB, committed in the repository. On the raw corpus a job finishes in about 140 ms and wall clock swings 46 percent between trials, which is too noisy to build a scaling curve on. The benchmarks therefore run on a replicated corpus built by the committed data/scale.sh: the same books copied under distinct document names, so per-record work is unchanged and only input volume grows. At 66 MB the same job's trial spread is 5.9 percent.

How the timing is taken

The standalone coordinator polls for completion once a second and sleeps a second before exiting, so every externally timed job lands on a one-second grid: 1, 2, 4 and 8 workers all measured 3010 ms ±4 ms. That is a measurement of sleep constants, not of the system. The harness instead drives the coordinator in-process and reads phase boundaries from inside it, which is what makes the millisecond figures above mean anything.

Correctness of every measured run

Each run hashes its output: all lines from every reduce partition, sorted, SHA-256. A fast run that is silently wrong cannot pass as a good number. The hash is invariant under split size, worker count and trial — verified in tests across 8, 17 and 55 map tasks — and identical across all ten points of both scaling sweeps.

Reproducing it

data/scale.sh 20 /tmp/corpus20
go run ./bench -input '/tmp/corpus20/*.txt' -workload invertedindex \
    -reduce 16 -split-bytes 4194304 -trials 5 -seed 1 \
    -wait-backoff 10ms -sweep 1,2,4,8,16

go build -o /tmp/chaosworker ./chaos/worker
go run ./chaos -input '/tmp/corpus5/*.txt' -worker /tmp/chaosworker \
    -reduce 8 -split-bytes 1048576 -trials 3 -task-timeout 2s

Limitations, and what I'd do next

The weakest part of this work is that it is all one machine with four cores. That shapes nearly every number above.

  • The knee is at four workers because the box has four vCPU. A multi-machine measurement would move it, and would also expose coordinator RPC cost that is invisible here at 0.2% of wall clock. The 16-worker point is oversubscription, not distribution.
  • Coordinator restart is not implemented, so the chaos matrix cannot include it. All task state is in memory; surviving a restart needs task states, attempt numbers and the committer of any in-flight commit written durably and replayed at startup. Claiming fault tolerance for the coordinator without that would be untested.
  • Polling with a short backoff is the wrong long-term answer. The coordinator should hold a request open until work exists rather than having workers ask again every 10 ms.
  • The reduce fan-in is the next thing to attack, not the scheduler: 160 partitions read per reduce task is what floors the reduce phase, and no amount of added workers moves it.
  • The straggler scan walks every task in the phase while holding the coordinator lock. Fine at 160 tasks, wrong at a million.
  • The slow worker is simulated by stretching task duration, which models a uniformly slow machine rather than one slow only at certain operations. RPC faults are injected in the client, not at the network layer.
  • Worker utilization is computed from committed tasks, so a worker whose every attempt lost the commit race does not appear in that list at all.
